## Симлинки

Обвязки инструментов — симлинки на канон, копий правил в них нет:

- `CLAUDE.md -> AGENTS.md`
- `GIGACODE.md -> AGENTS.md`
- `.claude/skills -> ../.agents/skills`
- `.gigacode/skills -> ../.agents/skills`

Файлы вида `CLAUDE.md`/`GIGACODE.md` с текстом «прочитай `AGENTS.md`» или с заголовком `# AGENTS.md` ссылками не являются и агента к канону не ведут.

### Windows

На Windows симлинк, выгруженный из git, может стать обычным файлом с текстом `AGENTS.md` вместо ссылки — тогда политика и навыки не загружаются. Обнаружив Windows, заменить:

- `CLAUDE.md` и `GIGACODE.md` — файлами с единственной строкой `@AGENTS.md` (явный импорт, поддерживается Claude Code и GigaCode CLI);
- `.claude/skills` и `.gigacode/skills` — каталогами с junction: `mklink /J .claude\skills .agents\skills`, либо копиями папок навыков. Импорт `@` для каталогов не работает.

Проверка на любой ОС: `ls -la` должен показывать `lrwxr-xr-x` и стрелку, `readlink <имя>` — целевой путь.

## Проверка и коммиты

### Линтер

- Перед завершением любой задачи прогонять `ruff check .`. Разрешения на запуск не спрашивать — это обязательная автоматическая проверка.
- Порядок: `ruff check .` → автоисправления только для ошибок своей правки (`ruff check . --fix`) → при расхождении с линтером применить `ruff format .` → повторный `ruff check .`.
- Задача не считается выполненной, пока `ruff check .` не проходит без ошибок.
- Ошибки, существовавшие до правки, не исправлять и не подавлять через `# noqa`: перечислить их в отчёте отдельно.
- Если `ruff` не установлен или запуск невозможен, сказать об этом явно и не выдавать задачу за проверенную.

### Коммиты

- На любую просьбу о коммите (в любой формулировке) сначала проанализировать изменения: `git status`, `git diff`, `git diff --staged`. Эти команды разрешены в рамках запроса на коммит.
- Затем показать сообщение на английском в формате Conventional Commits и готовую команду:

  ```
  <type>: <subject>
  git commit -m "<type>: <subject>"
  ```

- Типы: `feat`, `fix`, `chore`, `refactor`, `test`, `docs`, `style`. Subject — повелительное наклонение, без точки в конце, до 72 символов.
- После показа спросить, делать ли коммит. Выполнять только после явного согласия или прямой просьбы; отсутствие ответа согласием не считается.
- Если изменения не в индексе, показать `git add <файлы>` и включить это в вопрос.
- Несвязанные изменения — несколько коммитов, каждому своё сообщение.
- Если в диффе секреты (`.env`, токены, ключи), предупредить и не коммитить их.
- `push` не предлагать и не выполнять. Без отдельной просьбы также не делать `git commit --amend`, `--no-verify`, force-операции и не переписывать историю.
