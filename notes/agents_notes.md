# Конспект: Spec, AGENTS.md, Skills, MCP, Subagents и Hooks

Агент начинает каждую сессию с чистого контекста: он не помнит договорённостей, не знает правил проекта и не различает требование от пожелания. Механизмы ниже распределяют ответственность между носителями информации и отвечают на разные вопросы — от «что сделать» до «что выполнить автоматически».

## 1. Spec

**Spec** — письменная спецификация: что нужно получить и по каким критериям результат считается готовым.

Без неё агент восстанавливает требование из переписки и додумывает недостающее: границы задачи, формат результата, что считать ошибкой.

Состав:

- Цель и контекст: зачем нужно, что меняется.
- Функциональные требования: поведение, входы и выходы.
- Нефункциональные требования: производительность, совместимость, безопасность.
- Ограничения: что нельзя менять, какие зависимости допустимы.
- Критерии приёмки: проверяемые условия «готово».

```markdown
## Задача
Добавить обновление access-токена.

## Требования
- `POST /auth/refresh` принимает refresh-токен и возвращает новую пару.
- Просроченный refresh: ответ 401, запись в БД не создаётся.

## Ограничения
- Контракты `/auth/login` не менять.

## Критерии приёмки
- [ ] Тест на успешное обновление
- [ ] Тест на просроченный токен
```

Ключевое свойство — проверяемость. «Работает корректно» критерием не является, «просроченный refresh даёт 401» является.

Spec описывает одну задачу. Правила, действующие всегда, в него не помещаются: их пришлось бы повторять в каждой постановке.

## 2. AGENTS.md

**AGENTS.md** — файл проектных инструкций, который агент читает до начала работы. Отвечает на вопрос «по каким правилам здесь работают».

Содержит:

- Назначение проекта и его границы.
- Стек и версии.
- Структуру каталогов.
- Команды: установка, тесты, линтер.
- Правила кода и тестов.
- Ограничения: что нельзя трогать без согласования.

```markdown
## Проект
Сервис авторизации на FastAPI и PostgreSQL.

## Команды

| Задача | Команда |
|---|---|
| Тесты | `pytest` |
| Линтер | `ruff check .` |

## Ограничения
- Секреты только через переменные окружения.
- Миграции не менять без согласования.
```

Особенности:

- Файл читается целиком при каждом запуске, поэтому его объём — прямой расход контекста. Правило на 40 строк соблюдают чаще, чем файл на 500.
- Может лежать в корне и во вложенных каталогах: действует ближайший к файлу, вложенные дополняют корневой.
- Это открытый формат: его читают Codex, Cursor и другие агенты; Claude Code обращается к нему через `CLAUDE.md`, GigaCode — через `GIGACODE.md`.

Инструментов несколько, и каждый ищет своё имя файла. Копировать правила под каждое имя — значит получить несколько версий, которые разойдутся после первой правки. Как обойтись без копий — в примечании.

## 3. Skills

**Skill** — папка с файлом `SKILL.md`: процедура для повторяющегося типа задач. Отвечает на вопрос «как выполнять работу».

Файл начинается с frontmatter, в котором обязательны два поля:

```markdown
---
name: release-checklist
description: Подготовка релиза. Используй при сборке релизной ветки, образа и заметок о выпуске.
---

# Подготовка релиза

1. Проверь, что задачи релиза закрыты.
2. Собери заметки о выпуске из коммитов между тегами.
3. Собери образ и отметь версию.
```

- `name` — идентификатор, совпадает с именем папки.
- `description` — условие применения, а не заголовок. Агент видит только его и по нему решает, подключать ли навык.

Плохое описание: «Работа с релизами». Хорошее: «Подготовка релиза. Используй при сборке релизной ветки, образа и заметок о выпуске».

Навык — это каталог, а не один файл: рядом с `SKILL.md` можно держать шаблоны, скрипты и примеры, на которые ссылается инструкция.

Экономия контекста: в памяти агента находятся только имена и описания, текст навыка читается при совпадении задачи.

Ограничение: процедуры не дублируют в `AGENTS.md`, иначе навык и правило начнут расходиться.

## 4. MCP

**MCP (Model Context Protocol)** — открытый протокол подключения внешних систем к агенту. Отвечает на вопрос «с чем агент может работать».

Основные серверные примитивы:

- **tools** — действия: создать задачу, выполнить запрос;
- **resources** — данные: документы, записи, содержимое таблиц;
- **prompts** — шаблоны типовых сценариев.

Клиентские возможности дополняют их: **sampling** (запрос к модели через сервер), **roots** (границы доступных каталогов), **elicitation** (уточняющий вопрос пользователю).

Транспорт: `stdio` для локальных серверов, HTTP — для удалённых.

Подключение описывается списком серверов:

```json
{
  "mcpServers": {
    "notion": {
      "command": "npx",
      "args": ["-y", "<пакет-mcp-сервера>"],
      "env": { "NOTION_TOKEN": "${NOTION_TOKEN}" }
    }
  }
}
```

Ограничения: сервер получает ровно те права, которые ему передали; токены — только через переменные окружения; ответы внешней системы считаются данными, а не инструкциями.

## 5. Subagents

**Subagent** — отдельный агент, которому основной передаёт часть задачи. Отвечает на вопрос «кто выполнит работу».

- Собственный контекст: переписку не видит, получает только постановку.
- Собственные инструкции и набор инструментов.
- Возвращает результат, а не ход выполнения.

Пример: анализ архитектуры, подготовка тестов и проверка безопасности уходят трём подагентам, основной сводит ответы.

Ограничение: делегировать стоит независимые части. Задача, требующая общего контекста, в подагенте потеряет детали, поэтому постановка должна быть самодостаточной.

## 6. Hooks

**Hook** — команда, которую инструмент запускает на событие жизненного цикла. Отвечает на вопрос «что выполнять автоматически».

Хуки не универсальны: имена событий, способ настройки и формат конфигурации задаёт конкретный инструмент. В Claude Code они описываются в секции `hooks` настроек, а типичные события называются `PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit`.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "ruff check ." }]
      }
    ]
  }
}
```

Отличие от правила: правило просит агента, hook выполняет хост. Проверку, которая обязана случиться, надёжнее оформить хуком.

Ограничения: hook — это код, его ошибка блокирует работу; событие `Stop` срабатывает при завершении ответа, а не при завершении задачи.

## Как механизмы сочетаются

1. Spec фиксирует требование и критерии приёмки.
2. `AGENTS.md` задаёт постоянные правила, Skills — процедуры.
3. Основной агент планирует работу и при необходимости передаёт части Subagents.
4. MCP даёт доступ к внешним данным и действиям.
5. Hooks проверяют результат автоматически.
6. Итог — проверенная задача, а не черновик.

## Примечание: симлинки, импорты и сравнение

Инструменты ищут разные имена файлов инструкций. Чтобы не держать несколько копий правил, используют симлинки и `@`-импорт.

### Симлинки

**Symlink** — файл, который содержит путь к другому файлу или каталогу. Чтение ссылки открывает цель.

Файловые ссылки создаются по одной на каждое имя, которое ищет инструмент:

```bash
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md GIGACODE.md
```

Ссылки на каталоги навыков:

```bash
ln -s ../.agents/skills .claude/skills
ln -s ../.agents/skills .gigacode/skills
```

Проверка:

```bash
$ ls -la CLAUDE.md GIGACODE.md
lrwxr-xr-x  1 user  staff   9 Nov 22 10:00 CLAUDE.md -> AGENTS.md
lrwxr-xr-x  1 user  staff   9 Nov 22 10:00 GIGACODE.md -> AGENTS.md

$ readlink CLAUDE.md
AGENTS.md
```

Девять байт — это путь `AGENTS.md`, а не текст правил. Правка через любую сторону меняет один и тот же файл.

Правила создания:

- Цель указывается относительным путём: `AGENTS.md`, `../.agents/skills`. Абсолютный путь сломается при переносе репозитория.
- `ln -s` не перезаписывает существующее имя и завершается ошибкой `File exists`. Сначала удали файл `rm CLAUDE.md`, затем создай ссылку.
- `rm CLAUDE.md` удаляет только ссылку: файл `AGENTS.md` остаётся на месте.
- Форма `ln -sf` заменяет существующий объект по имени ссылки, поэтому применяется осознанно.
- На Windows файловая ссылка создаётся `mklink CLAUDE.md AGENTS.md` и требует прав администратора или режима разработчика; для каталогов используется junction. Надёжнее `@AGENTS.md` — см. раздел Windows.

Одно ограничение решает многое: файл-ссылку можно заменить `@`-импортом, каталог — нельзя, директива работает только с файлами.

### @-импорт

**@-импорт** — директива в тексте инструкций: инструмент подставляет содержимое указанного файла при загрузке.

```text
@AGENTS.md
```

Поддержка зависит от инструмента: Claude Code и GigaCode CLI понимают `@path`, остальные могут прочитать строку как обычный текст.

### Windows

Симлинк требует прав администратора или режима разработчика. Junction для каталогов прав не требует и не ломается при выгрузке из git:

```cmd
mklink /J .claude\skills %CD%\.agents\skills
mklink /J .gigacode\skills %CD%\.agents\skills
```

Для файлов инструкций вместо ссылки используется `@AGENTS.md` в `CLAUDE.md` и `GIGACODE.md`.

### Проверка и поломки

```bash
ls -la CLAUDE.md GIGACODE.md .claude/skills .gigacode/skills
readlink CLAUDE.md
```

Признак настоящей ссылки — тип `l` и стрелка с целевым путём в `ls -la`. Обычный файл показывает `-rw-r--r--`, а его размер равен размеру текста.

Два частых отказа:

- Удалён или перемещён целевой файл — ссылка становится битой, чтение даёт «No such file or directory».
- Вместо ссылки лежит обычный файл с текстом «прочитай `AGENTS.md`» или с заголовком `# AGENTS.md`. Агент увидит заголовок или фразу и ничего не загрузит.

### Сравнение

| Свойство | Симлинк | `@AGENTS.md` |
|---|---|---|
| Что лежит в файле | путь к цели | текст директивы |
| Кто разворачивает | операционная система | парсер инструмента |
| Где работает | любая программа | только инструменты с импортом |
| Windows без dev mode | ломается | работает |
| Каталоги | поддерживаются | не поддерживаются |

| Среда | Файлы инструкций | Каталоги навыков |
|---|---|---|
| Linux, macOS | симлинки | симлинки |
| Windows | `@AGENTS.md` | junction |

Копия вместо ссылки — антипаттерн: две копии правил расходятся при первой правке, и агенты начинают работать по-разным правилам.
