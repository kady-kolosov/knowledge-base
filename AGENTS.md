# AGENTS.md

## 1. О проекте

Репозиторий выполняет две функции:

1. **Переиспользуемый шаблон проекта** — основа, которую можно клонировать и адаптировать для начала разработки новых проектов без повторного создания базовой инфраструктуры.
2. **База технических знаний** — коллекция структурированных конспектов, примеров и объяснений, к которым можно обращаться во время обучения и разработки.

Основное направление проекта — E-commerce Backend на Python.

### Основные принципы

- Предпочитать понятные, поддерживаемые и предсказуемые решения излишней сложности.
- Следовать общепринятым практикам Python и существующим соглашениям проекта.
- Повторно использовать готовые утилиты, фикстуры, абстракции и примеры, если они подходят для задачи.
- Сохранять универсальность шаблона, не привязывая его без необходимости к особенностям одного приложения.
- Поддерживать техническую точность и последовательность учебных материалов.
- Не добавлять зависимости, архитектурные паттерны и абстракции без обоснованной необходимости.
- Не считать распространённую практику обязательным правилом проекта, пока это не подтверждено его конфигурацией или реализацией.

```bash

```

- Если файл или каталог появился, удалился или переименовался, обнови блок в этой же задаче.

## 3. Технологический стек

Используй зависимости, уже объявленные в проекте.

- Минимальная поддерживаемая версия: Python 3.14.

- **pytest** — тестовый фреймворк.
- **pytest-base-url** — настройка базового URL тестов.
- **pytest-xdist** — параллельное выполнение тестов.

- **python-slugify** — генерация slug.
- **ruff** — линтинг и форматирование Python-кода.

### Управление зависимостями

Зависимости ведутся двумя файлами:

- `requirements.in` — декларация прямых зависимостей с диапазонами версий. Источник истины для того, что проекту нужно.
- `requirements.txt` — полный лок с точными версиями, включая транзитивные. Источник истины для того, что фактически установлено.

Цикл работы:

```bash
pip install -r requirements.txt          # установка по локу
pip install --upgrade -r requirements.in # обновление из декларации
pip freeze > requirements.txt            # фиксация результата в локе
```

Необходимо:

- Проверять фактические зависимости перед использованием библиотеки.
- Повторно использовать существующие зависимости.
- Учитывать ограничения версий при написании кода.
- Не дублировать функциональность уже используемых библиотек.
- Держать декларацию и лок согласованными: после изменения окружения обновляй лок.

Запрещается без подтверждения пользователя:

- Добавлять или удалять зависимости.
- Обновлять или понижать версии библиотек.
- Изменять `requirements.in` и `requirements.txt` вне согласованного цикла обновления зависимостей.

Перезапись лока через `pip freeze > requirements.txt` в рамках согласованного цикла не требует отдельного подтверждения на каждую строку.

Не считай библиотеку доступной только потому, что она перечислена в этом документе. При необходимости проверяй фактическое окружение и конфигурацию.

### Общие правила

- При изменении поведения подготавливай соответствующие тесты.
- Проверяй наблюдаемое поведение, а не внутренние детали реализации без необходимости.

- Не ослабляй проверки только ради прохождения тестов.

### pytest

- Соблюдай существующую организацию тестов и правила именования.
- Используй фикстуры для повторно используемой подготовки и очистки окружения.

## 7. Линтинг и форматирование

Ruff — основной инструмент линтинга и форматирования Python-кода.

Перед завершением любой задачи выполни:

```bash
ruff check .
```

Запуск проверки файлы не изменяет, поэтому разрешения на него не спрашивай.

Если Ruff обнаружил ошибки:

1. Изучи каждую ошибку.
2. Исправь ошибки, появившиеся в результате текущих изменений.
3. Автоматические исправления используй только для ошибок, относящихся к текущей задаче:

```bash
ruff check . --fix
```

4. Если необходимо форматирование, примени:

```bash
ruff format .
```

5. Повтори финальную проверку:

```bash
ruff check .
```

### Важные ограничения

- Не исправляй автоматически старые ошибки, не относящиеся к задаче.
- Не подавляй существующие ошибки через `# noqa`.
- Не форматируй файлы, не относящиеся к задаче.
- Если финальная проверка обнаружила ранее существовавшие ошибки, перечисли их отдельно.
- Если Ruff не установлен или запуск невозможен, сообщи об этом явно.

Задача не считается выполненной, пока `ruff check .` не проходит без ошибок, появившихся в результате правки. Ранее существовавшие ошибки задачу не блокируют, но перечисляются в отчёте отдельно.

## 8. Git и коммиты

Работа с Git должна быть осознанной и прозрачной.

### Подготовка коммита

При просьбе подготовить или выполнить коммит сначала изучи:

```bash
git status
git diff
git diff --staged
```

Эти команды разрешены в рамках запроса на коммит.

Проверь:

- Посторонние изменения.
- Случайные удаления.
- Секреты и учётные данные.
- Сгенерированные файлы, которые не следует коммитить.
- Изменения за пределами задачи.

### Формат сообщения коммита

Используй Conventional Commits:

```text
<type>: <subject>
```

Допустимые типы:

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `chore` — обслуживание и инструменты.
- `refactor` — изменение структуры кода без изменения поведения.
- `test` — изменения тестов.
- `docs` — документация.
- `style` — форматирование и стиль без изменения поведения.

Требования:

- Сообщение пишется на английском языке.
- Subject формулируется в повелительном наклонении.
- Длина Subject — не более 72 символов.
- Точка в конце не ставится.

Пример:

```bash
git commit -m "docs: improve project agent instructions"
```

### Подтверждение коммита

Перед выполнением коммита:

1. Покажи предложенное сообщение.
2. Покажи команду `git add <файлы>`, если изменения ещё не добавлены в индекс.
3. Запроси подтверждение пользователя.

Выполняй коммит только после явного подтверждения или прямой просьбы выполнить коммит.

Прямая просьба выполнить коммит считается подтверждением, но сообщение и команду покажи и в этом случае.

### Несвязанные изменения

Если изменения не связаны между собой, разделяй их на логически независимые коммиты.

### Секреты

Если в diff обнаружены секреты, токены, пароли, приватные ключи или другие учётные данные:

- Предупреди пользователя.
- Не включай такие данные в коммит.
- Не показывай сами секретные значения в отчёте.
- Не выполняй несогласованную очистку файлов.

### Запрещённые операции

Без отдельной явной просьбы запрещено выполнять:

- `git push`.
- `git commit --amend`.
- Force push.
- Переписывание истории.
- Деструктивные операции сброса.
- Пропуск Git hooks через `--no-verify`.
- Другие деструктивные операции с Git.

Разрешение на коммит не означает разрешение на push.

Все существующие файлы и данные считаются пользовательскими.

**Любая операция, изменяющая состояние репозитория или пользовательских данных, требует предварительного подтверждения.**

Это правило распространяется на:

- Создание файлов и каталогов.
- Изменение существующих файлов.
- Перезапись содержимого.
- Удаление файлов и каталогов.
- Перемещение и переименование.
- Массовые преобразования.
- Изменение конфигурации.
- Изменение зависимостей.
- Запись и изменение данных в Notion.
- Изменение Git-индекса и истории.

Перед выполнением такой операции:

1. Объясни, что именно планируется изменить.
2. Укажи затрагиваемые файлы или данные.
3. Объясни существенные риски, если они есть.
4. Получи явное подтверждение пользователя.
5. Выполняй только подтверждённые действия.

Не считай разрешением на изменение:

- Просьбу изучить проект.
- Просьбу проанализировать код.
- Просьбу найти ошибку.
- Просьбу предложить решение.
- Просьбу объяснить, как что-либо исправить.
- Сам факт обнаружения проблемы.

Если пользователь попросил исправить, реализовать или обновить что-либо, сначала подготовь план и запроси подтверждение изменений.

Подтверждение распространяется только на согласованный объём работ. Для дополнительных изменений требуется отдельное разрешение.

Чтение, поиск, анализ и просмотр файлов разрешены без дополнительного подтверждения.

Исключение — обновление дерева репозитория в §2 при изменении структуры: это обслуживание документации, отдельное подтверждение не требуется.

## 10. Совместимость агентов и Skills

Репозиторий может использоваться разными агентами.

Канонический файл проектных инструкций — `AGENTS.md`.

Файлы и каталоги для конкретных инструментов должны ссылаться на канонические инструкции, а не содержать независимые копии правил.

### Канонические симлинки

Ожидаемые ссылки:

```text
CLAUDE.md -> AGENTS.md
GIGACODE.md -> AGENTS.md
.claude/skills -> ../.agents/skills
.gigacode/skills -> ../.agents/skills
```

Не поддерживай отдельные копии одинаковых проектных правил в файлах разных агентов.

Файл `CLAUDE.md` или `GIGACODE.md` с текстом «прочитай `AGENTS.md`» либо с заголовком `# AGENTS.md` ссылкой не является: агент увидит заголовок или фразу, но к канону не перейдёт.

### Windows

На Windows Git может выгрузить симлинк как обычный файл с текстом целевого пути вместо создания настоящей ссылки.

В результате инструкции и Skills могут загружаться неправильно.

Для файлов инструкций используй файл с единственной строкой:

```text
@AGENTS.md
```

Такой явный импорт поддерживается Claude Code и GigaCode CLI.

Для каталогов Skills используй junction или копии:

```cmd
mklink /J .claude\skills .agents\skills
mklink /J .gigacode\skills .agents\skills
```

Импорт через `@` для каталогов не работает.

### Проверка ссылок

В системах с поддержкой симлинков проверяй:

```bash
ls -la
readlink CLAUDE.md
readlink GIGACODE.md
readlink .claude/skills
readlink .gigacode/skills
```

Убедись, что ссылки ведут на ожидаемые канонические пути.

Настоящий симлинк в `ls -la` выглядит как `lrwxr-xr-x  CLAUDE.md -> AGENTS.md`: тип `l` и стрелка с целевым путём. Обычный файл с тем же именем показывает `-rw-r--r--`, а его размер — это размер текста, тогда как ссылка занимает единицы байт.

В Windows проверяй, являются ли соответствующие пути симлинками, junction или обычными файлами.

Не заменяй корректные ссылки и junction без необходимости.

### Skills

- Используй существующие Skills, если они соответствуют задаче.
- Перед специализированной работой изучи соответствующий `SKILL.md`.
- Не дублируй инструкции Skills в `AGENTS.md`.
- Общие правила проекта храни в `AGENTS.md`, специализированные процедуры — в соответствующих Skills.
- Не создавай и не изменяй Skills без подтверждения пользователя.

## 11. Порядок работы агента

Для каждой задачи:

1. Определи ожидаемый результат.
2. Изучи соответствующие файлы, конфигурацию и соглашения проекта.
3. Найди существующие решения и связанные тесты.
4. Определи минимальный объём необходимых изменений.
5. Подготовь план и перечисли файлы или данные, которые потребуется изменить.
6. Получи подтверждение пользователя.
7. Выполни только согласованные изменения.
8. Запусти необходимые тесты и проверки.
9. Изучи итоговый diff, если изменялись файлы.
10. Подготовь отчёт.

### Итоговый отчёт

После выполнения задачи укажи:

- Что было сделано.
- Какие файлы затронуты.
- Какие тесты и проверки запускались.
- Фактические результаты проверок.
- Какие проблемы остались.
- Что не удалось проверить и почему.

Не заявляй о выполнении или проверке действий, которые фактически не производились.

## 12. Приоритеты при принятии решений

При выборе реализации придерживайся следующего порядка:

1. Корректность важнее изобретательности.
2. Простота важнее неоправданных абстракций.
3. Существующие соглашения проекта важнее личных предпочтений.
4. Явное поведение важнее скрытых побочных эффектов.
5. Локальные изменения предпочтительнее масштабного рефакторинга.
6. Проверенные результаты важнее предположений.
7. Сохранность знаний и истории проекта важнее косметического единообразия.
8. При существенной неопределённости сначала запроси уточнение.

Главная цель — сохранять репозиторий одновременно удобным шаблоном для разработки и надёжной базой технических знаний.
